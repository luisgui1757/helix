# Second opinion inside T3 Code

Query `orchestrator_capabilities` for live provider instances, models, option
descriptors and constraints. A null `parentThreadId` in the response means this
session is not inside a T3 thread; use the direct-host consultation instead. If
the live schema offers a broader catalog view, such as all models rather than
favorites, request it and disclose any filter or omitted count the response
reports. Use `delegate_task` with exact requested
target fields; set `providerInstanceId` for a different provider, and `model`
only when requested or set by an applicable saved preference for that
provider/driver. Otherwise omit the model and report T3's returned choice.
Requested effort without a resolved model needs clarification or NOT RUN. Apply
effort through that model's advertised `target.options`, without inventing
option IDs or values; T3 accepting an option does not prove it applied. A model
absent from the visible catalog may be filtered out: retain a literal request
and let T3 validate it, but unresolved effort descriptors or unavailable
providers mean NOT RUN. Do not predict another provider's default model from
the filtered catalog; report the returned model. Different providers are
supported when requested and available; compare driver identity, because
another instance of the same driver is not a different provider. Do not
configure adapters or authentication.

Native reviewer roles and Codex `[agents]` defaults are not applied by T3
delegation. Disclose that boundary and honor relevant saved model/effort choices
through supported targets. Disclose unapplied native tool limits; the saved tool
list alone does not require enforced isolation in T3. Explicit user or
repository isolation requirements must still be met.

`role: review` is only an instruction, and a narrower runtime mode is not a
read-only switch. Apply available host restrictions and disclose any enforcement
gap; required isolation that is unavailable means NOT RUN. Leave the runtime
mode inherited unless the user asks otherwise. Inheritance uses the parent's
mode, stepped down to what the target provider offers, and can fall back to
`approval-required`; check the parent's `runtimeMode` and the target's
`runtimeModes` in the capabilities response. A supervised child usually pauses
for approvals the parent cannot give, so tell the user approvals may be needed
in its thread. Keep the default `isolation: shared` when the consultant must
read uncommitted files; a `worktree` child starts from the parent's last commit
without them, and a worktree is not a sandbox.

Follow `task_status` after a wait timeout without duplicating the task. Reading
a terminal result consumes its notification, so do not then wait for a wake.
Completion alone is not a useful opinion or approval. A later consultation needs
a new `delegate_task` and request ID. Messaging the old child may create a
follow-up task in its existing conversation, which is not a fresh independent
consultation.
