# T3 discovery and role choices

Inside T3, inspect the live `orchestrator_capabilities` response and delegation
schema. A null `parentThreadId` in the response means this session is not
inside a T3 thread; use the direct-host references instead. T3 owns its
provider/model/options catalog; do not run Helix's direct-CLI
discovery helper or maintain another catalog. List provider instances with driver
identity, advertised models, per-model options, child/cross-provider availability,
runtime modes and constraints. The returned models may be filtered by T3 hidden-model
preferences or another reported filter, such as favorites. Request the broadest
catalog view the live schema offers and disclose any remaining filter or omitted
count instead of claiming an exhaustive provider list.
A literal model absent from this view may still be dispatchable; let T3 validate
it, but do not invent missing effort descriptors. Missing credentials or a disabled provider must
remain visible. Catalog membership does not prove access.

Keep the current writer unless asked otherwise. Support a reviewer on a different
provider; two accounts on one driver do not meet a different-provider request.
In guided T3 setup, collect any missing provider-instance choice before the model
and effort choices, and include it when listing missing choices. Offer
"provider default: T3 chooses; reported after dispatch"
alongside the literal models; a changed provider does not inherit the writer's model.
Resolve explicit models literally and reasoning effort from the selected model's
advertised option IDs/values. Do not invent a shared effort enum. Confirmed unsupported or
ambiguous requests remain unresolved; never substitute another model or effort.
Follow the skill's complete-catalog, missing-choice and preview rules. For
task-scoped choices, ask Use/Cancel and state that nothing is persisted. Use
Save/Cancel only for an actual edit to T3 settings through a supported operation.

For a different provider, set `providerInstanceId`; `model` is optional unless
requested or set by an applicable saved preference for that provider/driver.
Optional `options` use `[{id, value}]` or the record form supported by the live schema. A changed provider does
not inherit the writer's model/options; when no model is supplied T3 can choose
from an internal list that differs from the visible catalog. Report its returned
model instead of predicting that default. If the model is left to T3's default,
keep effort at its default or ask for a model before resolving requested effort.
Do not dispatch while a requested effort remains unresolved.
Choosing roles does not switch the running writer or prove settings were saved.
T3 delegation does not apply native Claude reviewer roles or Codex `[agents]`
defaults. Disclose that boundary; existing explicit reviewer model/effort choices
need supported T3 targets, and native tool restrictions cannot be presumed.
A saved native tool list alone does not require enforced isolation in T3;
disclose unapplied limits. Explicit user or repository isolation requirements
remain binding and block dependent dispatch if unavailable.

Use supported T3 UI/settings operations only when available and authorized.
The inspected orchestration tools do not expose a persistent Helix-role settings
API. Otherwise provide exact per-task choices for a new thread or delegation,
label them task-scoped, and do not create a Helix config format, edit T3 databases,
or write direct Codex/Claude role files as a substitute for T3 settings.
Do not configure authentication, trust, permissions or provider adapters.

An authorized execution probe must use a fresh T3 task and record the returned
provider/model plus correlated native model-option evidence where exposed.
An accepted request or an agent self-report is not proof of effective effort.
Report configured/requested, observed and unverified settings separately.
`role: review` supplies instructions, not an enforced read-only sandbox: use
available host restrictions and disclose the enforcement gap. Leave the probe's
runtime mode inherited; if it resolves to a supervised mode, the child may wait
for approvals in its own thread that the parent cannot give. A completed probe
does not certify Helix delivery or review.
